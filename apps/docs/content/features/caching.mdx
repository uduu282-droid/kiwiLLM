# Caching

KiwiLLM can cache identical requests so repeated prompts return faster and avoid unnecessary provider calls.

## How it works

When caching is enabled:

1. KiwiLLM computes a cache key from the request payload
2. If a matching cached response exists, it is returned immediately
3. If not, the request goes to the upstream provider
4. The response is stored for future identical requests

This is most useful for repeated prompts, testing loops, FAQ flows, and retry-heavy workloads.

## What affects the cache key

The cache key is derived from request inputs such as:

- model
- messages
- temperature
- max tokens
- tools and tool choice
- response format
- system instructions

Even small differences in those inputs create a different cache entry.

## Requirements

Caching depends on data retention being enabled, because KiwiLLM needs to persist request and response payloads.

<Callout type="warning">
	Enable [Data Retention](/features/data-retention) before turning on caching.
</Callout>

Then:

1. Enable retention for the organization
2. Turn on caching in project preferences
3. Set an appropriate cache TTL
4. Send requests normally

## Cache hits and misses

### Cache hit

- response returns immediately
- no upstream provider call
- no new inference cost

### Cache miss

- request is sent upstream
- normal inference cost applies
- response is stored for later reuse

## Streaming support

Caching works with both standard and streaming responses.

- Non-streaming responses are returned directly from cache
- Streaming responses are reconstructed and streamed back from cached content

## TTL

Cache duration is configurable per project. Short TTLs are useful for frequently changing information, while longer TTLs work well for static prompts and repeated workloads.

## Example cached usage

Cached responses typically show zero or near-zero inference usage:

```json
{
	"usage": {
		"prompt_tokens": 0,
		"completion_tokens": 0,
		"total_tokens": 0,
		"cost_usd_total": 0
	}
}
```

## Best practices

- Use stable prompt formatting
- Normalize inputs before sending
- Prefer deterministic settings when you want high cache reuse
- Avoid timestamps or random values in prompts you expect to cache

## Storage cost note

If retention is enabled, storage cost applies separately from inference cost. See [Cost Breakdown](/features/cost-breakdown) and [Data Retention](/features/data-retention) for the related billing details.

<Callout type="info">
	For workloads with repeated prompts, cache savings usually outweigh storage
	costs by a wide margin.
</Callout>
