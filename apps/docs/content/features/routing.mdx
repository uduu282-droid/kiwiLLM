# Routing

KiwiLLM supports three routing styles:

1. **Model routing** to the best provider for a model
2. **Provider-specific routing** when you want a fixed upstream
3. **Auto routing** when you want KiwiLLM to choose the model for you

## Model routing

If you send only a model ID, KiwiLLM routes the request to the best available provider for that model.

```bash
curl -X POST "https://api.kiwillm.in/v1/chat/completions" \
  -H "Authorization: Bearer $KIWILLM_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-4o",
    "messages": [{ "role": "user", "content": "Hello!" }]
  }'
```

This is the best default for most production workloads because it lets KiwiLLM optimize for reliability, latency, and cost without changing your application code.

## Provider-specific routing

If you want a specific upstream, prefix the model with the provider name:

```bash
curl -X POST "https://api.kiwillm.in/v1/chat/completions" \
  -H "Authorization: Bearer $KIWILLM_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "openai/gpt-4o",
    "messages": [{ "role": "user", "content": "Hello!" }]
  }'
```

You can use this pattern with built-in providers and custom providers.

<Callout type="info">
	Use provider-specific routing when you need deterministic upstream behavior
	for testing, benchmarking, or vendor-specific capabilities.
</Callout>

## Automatic fallback

When KiwiLLM controls routing, failed providers can be retried automatically on the next best provider for the same model.

Retries are typically triggered by:

- upstream `5xx` errors
- connection failures
- timeouts

Retries are not used for client-side request errors like `400`, `401`, or `422`.

```text
Request -> Provider A fails -> Provider B succeeds -> Response
```

Both standard and streaming completions support fallback.

## Disabling fallback

If you need to force the exact provider you requested, send the `X-No-Fallback: true` header:

```bash
curl -X POST "https://api.kiwillm.in/v1/chat/completions" \
  -H "Authorization: Bearer $KIWILLM_API_KEY" \
  -H "Content-Type: application/json" \
  -H "X-No-Fallback: true" \
  -d '{
    "model": "openai/gpt-4o",
    "messages": [{ "role": "user", "content": "Hello!" }]
  }'
```

<Callout type="warning">
	Disabling fallback means KiwiLLM will not fail over to another provider if the
	selected upstream is degraded or unavailable.
</Callout>

## Auto routing

Set `"model": "auto"` to let KiwiLLM select the model itself:

```bash
curl -X POST "https://api.kiwillm.in/v1/chat/completions" \
  -H "Authorization: Bearer $KIWILLM_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "auto",
    "messages": [{ "role": "user", "content": "Summarize this document." }]
  }'
```

Auto routing is useful when you want KiwiLLM to handle model selection based on request shape, context size, and available capabilities.

### Free models only

You can restrict auto routing to zero-cost models by adding `free_models_only`:

```bash
curl -X POST "https://api.kiwillm.in/v1/chat/completions" \
  -H "Authorization: Bearer $KIWILLM_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "auto",
    "free_models_only": true,
    "messages": [{ "role": "user", "content": "Hello!" }]
  }'
```

### Reasoning-aware routing

If you set `reasoning_effort`, KiwiLLM restricts selection to reasoning-capable models:

```bash
curl -X POST "https://api.kiwillm.in/v1/chat/completions" \
  -H "Authorization: Bearer $KIWILLM_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "auto",
    "reasoning_effort": "medium",
    "messages": [{ "role": "user", "content": "Solve this step by step." }]
  }'
```

If you want to exclude reasoning models, set `no_reasoning: true`.

## Best practices

- Use plain model IDs in most production traffic
- Use provider-prefixed models for testing and debugging
- Use `"model": "auto"` when you want KiwiLLM to optimize selection
- Keep fallback enabled unless you have a strong reason to pin one provider
- Review logs and cost data to understand how traffic is being routed

<Callout type="success">
	KiwiLLM is most valuable when you let it absorb provider outages and routing
	decisions for you. Start with model routing, then tighten controls only where
	you actually need them.
</Callout>
