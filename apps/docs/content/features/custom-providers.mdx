# Custom Providers

KiwiLLM lets you register custom OpenAI-compatible providers so you can route traffic to private models, internal gateways, or third-party services that are not built in by default.

Typical use cases:

- self-hosted or on-prem model endpoints
- internal company inference services
- OpenAI-compatible proxies
- experimental providers you want to test before wider rollout

## What counts as compatible

Your upstream should behave like an OpenAI-style chat completions API.

At minimum, it should support:

- a base URL
- bearer-token authentication, if required
- OpenAI-style `/v1/chat/completions` requests and responses

<Callout type="info">
	KiwiLLM does not need the upstream to be one of the built-in providers. It
	just needs a stable OpenAI-compatible interface.
</Callout>

## Setup flow

### 1. Add the provider in the dashboard

In your organization settings, add a custom provider key and supply:

- a lowercase provider name
- the upstream base URL
- the upstream API token, if the service requires one

### 2. Route requests using the provider prefix

Once configured, call the provider with:

```text
{providerName}/{modelName}
```

Example:

```bash
curl -X POST "https://api.kiwillm.in/v1/chat/completions" \
  -H "Authorization: Bearer $KIWILLM_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "mycompany/custom-gpt-4",
    "messages": [
      {
        "role": "user",
        "content": "Hello from our custom provider."
      }
    ]
  }'
```

## Naming rules

Custom provider names must use lowercase letters only.

Valid examples:

- `mycompany`
- `internal`
- `testing`

Invalid examples:

- `MyCompany`
- `my-company`
- `my_company`
- `123test`

## Base URL behavior

Use the upstream base URL, not the full chat completions path.

Example:

```text
https://api.example.com
```

KiwiLLM will construct the final request path from there.

## Tokens and auth

If your upstream requires bearer auth, store that token in the custom provider config.

If your upstream is intentionally no-auth, KiwiLLM can still route to it as long as the provider is configured accordingly.

## What you still get

Custom providers still benefit from the rest of KiwiLLM:

- API key auth for your users
- usage logs
- cost tracking, when pricing is configured
- request history
- project-level governance
- consistent OpenAI-compatible client usage

## Best practices

- start with one or two models first
- verify request and response compatibility before broader rollout
- keep provider names short and stable
- document internal providers clearly for your team
- add health checks or fallback policies if the upstream is business-critical

<Callout type="warning">
	KiwiLLM cannot guarantee compatibility if the upstream only partially matches
	the OpenAI schema. Test streaming, tool calls, and response shapes before
	exposing a custom provider to production traffic.
</Callout>
