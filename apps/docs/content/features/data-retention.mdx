# Data Retention

KiwiLLM supports configurable data retention so you can decide how much request data is stored for observability, debugging, and compliance workflows.

## Retention modes

KiwiLLM supports two main retention levels at the organization level:

| Level             | Description                                                                 |
| ----------------- | --------------------------------------------------------------------------- |
| `metadata_only`   | Stores lightweight request metadata like timestamps, model, usage, and cost |
| `retain_all_data` | Stores full request and response payloads for deeper inspection             |

<Callout type="info">
	Metadata-only retention is the safer default when you want usage analytics
	without storing full prompts and responses.
</Callout>

## When full retention helps

Retaining full payloads is useful when you need to:

- inspect exact prompts sent in production
- review tool calls and model outputs
- debug routing or response issues
- maintain a stronger audit trail for internal workflows

## Storage cost

When full retention is enabled, storage cost is reported separately from inference cost through `cost_usd_data_storage`.

See [Cost Breakdown](/features/cost-breakdown) if you want to read that field programmatically in API responses.

## How to configure it

In the dashboard:

1. Open organization settings
2. Go to policies
3. Choose the retention mode
4. Save the change

Retention changes apply to new traffic going forward.

## Retention period

Hosted deployments retain data for the configured platform period. Self-hosted deployments keep full control over retention duration because the data stays in your own infrastructure.

## Billing behavior

In hosted KiwiLLM, storage-related cost is tracked separately from token inference cost.

- inference cost covers the model call itself
- storage cost covers retained request and response data

If you are using features like [Caching](/features/caching), retention becomes especially important because cached and stored request data rely on the same observability layer.

## Best practices

- start with metadata-only if you are unsure
- enable full retention only where the debugging value is worth it
- review retention settings at the organization level, not just project by project
- avoid retaining sensitive production data longer than necessary

<Callout type="warning">
	If your workloads include sensitive user data, make sure your retention policy
	matches your privacy, security, and compliance requirements.
</Callout>
