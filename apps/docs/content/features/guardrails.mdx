# Guardrails

Guardrails help you inspect and control risky content before it reaches an upstream model.

They are useful for organizations that want additional protection around:

- prompt injection attempts
- jailbreak patterns
- secrets and credentials
- personally identifiable information
- restricted terms or sensitive internal topics

## How guardrails work

At a high level:

1. a request reaches KiwiLLM
2. content is checked against enabled rules
3. KiwiLLM decides whether to block, redact, or allow the request
4. the action is logged for review

## Common rule types

- prompt injection detection
- jailbreak detection
- PII detection
- secrets detection
- blocked terms
- custom regex patterns
- file-type restrictions

## Available actions

| Action   | Result                                         |
| -------- | ---------------------------------------------- |
| `block`  | Reject the request before it reaches the model |
| `redact` | Remove or mask matched content and continue    |
| `warn`   | Log the event but allow the request            |

## Recommended rollout

Start in `warn` mode first. That gives you a chance to learn what real traffic looks like before you begin blocking or redacting requests in production.

Then:

1. review violations
2. tune noisy rules
3. promote high-confidence rules to `block` or `redact`

## Good use cases

- preventing prompt injection in internal copilots
- masking emails, phone numbers, or secrets
- blocking uploads or prompts that contain forbidden patterns
- adding policy checks before sensitive tool-enabled agents run

<Callout type="warning">
	Guardrails work best as a layered control. They reduce risk, but they should
	not be the only safety mechanism in an application that handles sensitive
	workflows.
</Callout>
